# Geist milestone reality audit — 2026-07-13

## Verdict

Milestone 4 is not product-complete. Phase 31 delivered most of the repository scaffold but its claimed hard import boundary has an allowlist loophole, so it is reopened for a focused correction. Phases 32–39 contain useful isolated primitives, but their production composition, Quest client, and user-facing flows are incomplete. Phase 40 has no implementation beyond recording H8 as evidence debt.

The previous completion decision conflated four different states:

1. source or data structures exist;
2. a package-level unit/subsystem test exists;
3. the behavior is reachable through the production `geist` executable;
4. the behavior is verified on a physical Quest 3.

Only the first two are substantially represented in the repository. The third is absent for the core product flow, and every H0–H8 hardware gate remains unverified.

## Audit method

Five agents audited the repository in parallel:

- Quest/Spatial SDK and headset responsibilities;
- bridge, protocol, config, and voice;
- console, picker, and user flows;
- automated acceptance evidence;
- core, ACP, draht-acp, and security.

The audit was source-based; the agents did not run tests. Separately, the current plain Android scaffold was built with Gradle 8.7/JDK 17 using `:app:installDebug`, installed on a Quest 3 running Android 14/API 34, and launched as `dev.draht.geist/.MainActivity` on 2026-07-13. The build reported 36 successful tasks and installation on one device; the process launched but displayed a blank conventional Android activity. This is corroborating audit evidence, not H0 evidence: no Spatial SDK frame, coordinate log, screenshot, or alpha result was produced.

## Decisive evidence

- `packages/geist/src/cli.ts` prints `not implemented yet` and exits.
- `packages/geist/src/index.ts::runGeist()` always throws.
- The CLI does not read `geist.yaml`, start HTTP/WS services, serve `/ui`, create registries/worktrees, or launch ACP sessions.
- `quest/` has no Meta Spatial SDK dependency, spatial activity, scene, WebView, WS client, PTT/audio, crop, board, cards, lanes, variants UI, anchors, or persistence.
- `PassthroughPanel.attach()` and `detach()` are no-ops; `MainActivity` creates no content.
- `geist-console` renders only the `geist` wordmark and explicitly says cards, chips, palette, and lanes are absent.
- `geist-picker` only describes a supplied DOM element; it has no injectable IIFE, hover runtime, target ring, freeze, or crop capture.
- `scripts/check-geist-mirrors.mjs` checks an empty `MIRRORED_SCHEMAS` list, so no TypeScript protocol schema is mirrored in Kotlin.
- There is no production path joining WS pairing, voice, grammar, context composition, ACP, Git review, permissions, fleet state, variants, lanes, and Quest rendering.

## What existing tests actually prove

The repository has meaningful lower-level evidence:

- real local WebSocket pairing/reconnect against a JavaScript client;
- real ACP stdio subprocess round trips against a deterministic mock agent;
- a real Geist ACP client to draht-acp shim round trip using Draht's faux provider;
- real temporary Git repositories for ledger, fleet, and variant-domain tests;
- pure tests for grammar, project discovery, prompt shape, fleet projection, and lane recognition.

They do not prove a Geist end-to-end flow. Tests stop at package boundaries and often use fake sessions, literal capability objects, handcrafted event JSON, independent temporary repositories, or direct callbacks. No test launches the production `geist` binary and drives it exclusively through the headset protocol.

The following previous claims are therefore withdrawn:

- that a Meta Spatial SDK panel renders;
- that bridge↔Quest pairing and DE/EN voice are wired;
- that a crop is always written;
- that one fake-headset e2e covers ACP, permissions, review, approve/undo, and stop;
- that voice input spawns the right harness/project;
- that fleet cards, variants, or lanes render;
- that only hardware evidence remains;
- that Phase 40 can be complete by recording absent H8 evidence.

## Security disposition

See [`SECURITY-2026-07-13.md`](./SECURITY-2026-07-13.md) for the exhaustive, stable finding set: GSEC-01 through GSEC-13, with severity, owner, remediation, and closure evidence. It contains one Critical, eight High, three Medium, and one Low finding.

Do not expose the current pairing helper on LAN. It currently has no hostname option, so loopback cannot be enforced by callers. Phase 33 must first implement GSEC-04's loopback default; only then may development use `adb reverse`. Secure LAN/device binding remains required before LAN operation. `draht-acp` must not be represented as safely headset-permissioned until GSEC-01 and GSEC-02 are closed.

## Re-acceptance strategy

### Gate A — bootable composition

The emitted `geist` CLI must load and validate config, start one owned HTTP/WS process, serve `/ui`, manage shutdown, and expose a health endpoint. A test must launch the emitted binary rather than importing internals.

### Gate B — hermetic public-protocol e2e

A protocol-faithful fake headset must pair through WS, spawn a named mock ACP session from user-owned config in a real linked worktree, dispatch, receive tools/plans/permissions/fleet state, deny and allow permissions, reach review, approve and restore under the full-state semantics required by GSEC-05, run variants, select a winner, and clean up every process/worktree.

### Gate C — real browser UI

Browser automation must verify the board, cards, badges, permission chips, command/mode palette, variants row, lanes, LOOP context, and action state transitions through the same bridge protocol.

### Gate D — Quest M0/M1

Use the current official Meta Spatial SDK baseline, render a real URL panel, pair/reconnect from Kotlin, wire ray targeting and PTT audio, and archive H0/H1 evidence from the physical Quest 3. As of this audit, the official sample baseline is Spatial SDK 0.13.1, AGP 8.11.1, Kotlin 2.1.0, Gradle 9.4.1, and JDK 17; verify again when implementation starts.

### Gate E — remaining hardware evidence

Execute H2–H8 only after the software path each gate exercises exists. Archive commit, APK/build identifiers, headset/OS/SDK versions, protocol logs, screenshots/video, transcript scoring, crop artifacts, OVR metrics, and pose deltas.

## Implementation order

1. Phase 31: close the boundary-gate loophole and add a negative regression.
2. Phase 32: real Spatial SDK panel and ray input.
3. Phase 33: production bridge, minimal named mock session/dispatch, Quest pairing/PTT voice, and Kotlin protocol mirrors.
4. Phase 34: actual picker/crop/context loop on that minimal session path.
5. Phase 35: complete ACP review/permission lifecycle and close its release-blocking security findings.
6. Phases 36–39: commands, fleet, variants, and lanes through one public protocol/UI path.
7. Phase 40 only after the v1 core loop is accepted.

The smallest cognitively complete product slice remains: **one app panel → point → hold PTT → speak → one Draht ACP session receives the context-packed prompt and returns a visible result/permission state.** Fleet, variants, and spatial persistence should not delay that first accepted loop.
