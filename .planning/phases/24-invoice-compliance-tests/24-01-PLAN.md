# Phase 24, Plan 1: Invoice/Compliance Tests

## Goal
`packages/invoice` and `packages/compliance` ship real client/scanner code
(Phases 16-17) but most of it has no test coverage: `lexoffice.ts` (94 lines)
and `toggl.ts` (60 lines) have zero tests; `eu-ai-act.ts` (145 lines) has zero
tests; `gdpr-scanner.ts` has only single-line synthetic snippet tests, not a
realistic German-text corpus. This phase closes those four gaps.

## Context
- Both `packages/invoice` and `packages/compliance` use `bun:test` (not
  vitest) — match `packages/compliance/test/gdpr-scanner.test.ts`'s existing
  style (`import { describe, expect, test } from "bun:test";`).
- `LexofficeClient` and `TogglClient` both call the global `fetch` directly —
  no injectable HTTP client — so mocking means stubbing `globalThis.fetch`
  for the duration of each test and restoring it afterward.
- `GdprScanner.scanDirectory(dir)` scans a real directory on disk (see
  existing test's `mkdtempSync`/`writeFileSync` pattern) — the German-corpus
  test should follow the same fixture style, just with realistic multi-line
  German text (real names, Steuernummer/IBAN formats, addresses) instead of
  single hardcoded lines.
- `EuAiActChecker.checkProject(projectDir)` reads a doc file from a fixed set
  of candidate paths (see `docPaths` in `eu-ai-act.ts`) and checks each of
  the 6 `AI_DOC_REQUIREMENTS` sections by heading/ID/article/phrase-overlap
  matching.

## Risks
- Both invoice and compliance packages use `bun:test`, not vitest — the
  workflow must run `bun test` (via `npm test` in each package) for
  verification, not `npx vitest run`.
- Stubbing `globalThis.fetch` must restore the original after each test
  (via `afterEach`) so tests don't leak state into the rest of the suite.

## Out of Scope
- No changes to `lexoffice.ts`/`toggl.ts`/`eu-ai-act.ts`/`gdpr-scanner.ts`
  source behavior unless a real bug is found while writing tests against
  them (this phase is test-coverage, not a feature phase).
