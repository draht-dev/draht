# Phase 26, Plan 1: RLM Core Primitives

## Goal
Build `@draht/rlm`'s root loop: root-LLM-produces-code → REPL-executes →
truncated-stdout → history-append → FINAL-check, with `llm_query` and
`FINAL`/`FINAL_VAR` sentinels — the inference-time scaffold from Zhang,
Kraska, Khattab (2026), *Recursive Language Models* (arXiv:2512.24601).

## Explicitly out of scope for this phase (owned by later phases — do not build these now)
- **Real LLM wiring** (Phase 27): `llm_query` must be *injectable* here (a
  TypeScript callback passed into `RlmSession`), not hardcoded to
  `@draht/router`. Tests use a mock; production wiring happens in 27.
- **Sandboxing/resource limits** (Phase 28): no seccomp/ulimit, no network
  blocking, no `max_iterations`/`max_sub_calls`/cost budgets yet. The REPL
  subprocess in this phase is a plain, unsandboxed `python3` child process.
  Don't build safety mechanisms here — Phase 28 owns them and will wrap this
  phase's executor, not rewrite it.
- **CLI/agent integration** (Phase 29) and **eval/observability** (Phase 30).

## Architecture

### 1. Package scaffold (`packages/rlm/`)
Standard workspace package: `package.json` (name `@draht/rlm`), `tsconfig.json`,
`vitest.config.ts` (this monorepo mixes `bun:test` and `vitest` per package —
use vitest here to match `packages/router`, since RLM sessions will
eventually consume `@draht/router` types in Phase 27). `src/index.ts` barrel.

### 2. Python REPL driver (`packages/rlm/python/repl_driver.py`)
A small, dependency-free (stdlib only) Python script, spawned once per
`RlmSession` via `child_process.spawn("python3", [driverPath])` and kept
alive for the session's lifetime so variables persist in one `exec()`
globals dict across steps.

**Wire protocol**: newline-delimited JSON on stdin/stdout (avoids fragile
stdout-marker parsing). Node → driver messages:
```
{"type": "exec", "code": "<python source>"}
{"type": "llm_query_response", "id": "<uuid>", "text": "<result>"}
```
Driver → Node messages:
```
{"type": "llm_query_request", "id": "<uuid>", "prompt": "<prompt>"}
{"type": "exec_result", "stdout": "<captured stdout>", "error": "<traceback or null>", "final": null | {"kind": "value", "value": "<str>"} | {"kind": "var", "name": "<var name>", "value": "<repr'd value>"}}
```
Driver loop: read one `exec` message → `exec(code, globals_dict)` with
stdout captured via `contextlib.redirect_stdout` → write one `exec_result`.
If code calls the injected `llm_query(prompt)` function, that function
writes an `llm_query_request` to stdout and **blocks reading stdin** for the
matching `llm_query_response` (by `id`) before returning the text — this is
the RPC-over-pipes mechanism that lets Python code call back into
TypeScript (and therefore into a real or mocked LLM) mid-execution.

### 3. FINAL / FINAL_VAR — as function calls + a caught exception, not text parsing
Inject `FINAL(answer: str)` and `FINAL_VAR(name: str)` as Python functions in
the exec globals. Both raise a driver-internal `_RlmFinal` exception carrying
`{"kind": "value"|"var", ...}`. The driver's exec wrapper catches
specifically `_RlmFinal` (not bare `except Exception`) and reports it via the
`exec_result.final` field. This is the "brittleness safeguard" R26-RLM.6
asks for: because it's a real function call caught as a real exception,
there's no ambiguity from `FINAL(...)` appearing inside a string, a comment,
or a code block in stdout the way a text-pattern-matched sentinel would have.
`FINAL_VAR(name)` additionally does `repr(globals_dict[name])` — raise a
clear Python `NameError`-derived message if `name` isn't defined, don't let
`KeyError` leak as a raw driver crash.

### 4. `RlmSession` (`packages/rlm/src/session.ts`)
```ts
interface RlmSessionOptions {
  prompt: string;                          // becomes the `context` variable
  rootLlm: (history: RlmHistoryEntry[]) => Promise<string>; // returns python source (may be fenced in ```repl or ```python)
  llmQuery?: (prompt: string) => Promise<string>; // injectable; Phase 26 tests supply a mock
  maxIterations?: number;                  // soft cap only in this phase — hard enforcement is Phase 28
  stdoutTruncateChars?: number;            // default small cap, e.g. 2000
}
interface RlmResult { kind: "final" | "final_var" | "max_iterations" | "error"; value?: unknown; steps: number; history: RlmHistoryEntry[] }
class RlmSession {
  constructor(opts: RlmSessionOptions);
  async step(): Promise<RlmHistoryEntry>;   // one root-LLM turn: get code, exec, append history, may resolve final
  async run(): Promise<RlmResult>;          // loops step() until final/max_iterations/error
  dispose(): void;                          // kill the python subprocess
}
```
- On construction, spawn the driver, send an initial `exec` seeding
  `context = <the prompt, json-escaped>` into the namespace, and also inject
  `llm_query` (wired through the RPC mechanism above) — but note `llmQuery`
  the *TypeScript* callback is what actually answers `llm_query_request`
  messages; the Python-side `llm_query` function is just the RPC client.
- Root loop per `step()`: call `opts.rootLlm(history)` → parse a ```repl or
  ```python fenced code block out of its response (R26-RLM.4's "parse
  \`\`\`repl Python block" — support both fence languages) → send as `exec`
  to the driver → while driver emits `llm_query_request` messages, answer
  each via `opts.llmQuery` (throw a clear error if `llmQuery` wasn't
  provided and one is requested) → on `exec_result`, truncate `stdout` to
  `stdoutTruncateChars` with an explicit `[truncated N chars]` marker
  (matching R28-SBX.4's format now, even though enforcement of the cap as a
  hard safety limit is Phase 28's job) → append a **constant-size** history
  entry (R26-RLM.7): `{ step, code, truncatedStdout, error, timestamp }` —
  never append the full `context` itself into the history the root LLM sees
  again, only short metadata (context length, not content).
- `run()` stops on: driver reports `final` (kind "value" or "var" →
  resolve the actual value, doing the `FINAL_VAR` lookup client-side isn't
  needed since the driver already `repr()`'d it — but do note in code
  whether that repr needs `ast.literal_eval` or safe-eval to get a real JS
  value back, or whether `RlmResult.value` is allowed to just be the string
  repr for this phase, and say which you chose and why in the summary),
  `maxIterations` reached, or an unrecoverable driver error.

### 5. Cost/observability
Out of scope for real cost tracking (Phase 27/30), but `RlmHistoryEntry`
should already have the shape that later phases will extend, not need a
breaking change.

## Risks
- Bidirectional subprocess RPC (driver blocks on stdin mid-`llm_query`) is
  the trickiest part — get the driver test (task 2) fully solid before
  building `RlmSession` on top of it in task 3.
- `python3` availability: confirmed present in this dev environment
  (`/opt/homebrew/bin/python3`, 3.14.5) — don't add a runtime check that
  hard-fails on other minor versions; stdlib-only code should be broadly
  compatible.
- Don't build Phase 28's sandboxing here — an unsandboxed subprocess is the
  correct scope for this phase; resist the urge to add resource limits now.

## Out of Scope
- Real `@draht/router` wiring for `llm_query`/root LLM (Phase 27).
- Any sandboxing, resource limits, or budget enforcement (Phase 28).
- CLI/`/rlm` command, `rlm_query` tool (Phase 29).
- Trajectory JSONL logging, replay, eval harness (Phase 30).
