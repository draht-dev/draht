## Notes
- **Model choices for `rlm-root`/`rlm-sub` — no deviation from the plan's suggestion.** Both roles were added exactly as the plan's Architecture section 1 proposed, since they passed `config.ts`'s registry validation as-is:
  - `rlm-root`: primary `anthropic/claude-opus-4-6` (1M context window per `packages/ai/src/providers/anthropic.models.ts`), fallback `google/gemini-2.5-pro`.
  - `rlm-sub`: primary `google/gemini-2.5-flash` (fast/cheap), fallback `openrouter/deepseek-v3.2`.
  No substitution was needed; the plan's suggested models registered cleanly.
- **`selectTier` thresholds chosen: `>= 500_000` → `frontier`, `>= 128_000` → `coder-mid`, else → `small-context`.** Rationale documented directly in `prompts.ts`'s docstring: 500k+ tracks genuinely huge windows (1M-context Claude/Gemini variants) that can afford a terser prompt even after Phase 26's constant-size history metadata accumulates over many steps; 128k-500k is the most common modern context ceiling (GPT-4-class, Claude default, DeepSeek-V3) and gets a step-by-step prompt without being wastefully verbose; below 128k gets the most explicit scaffolding and smallest suggested chunk/peek sizes since the prompt itself is a proportionally larger share of the budget. Both boundaries (`500_000`/`499_999` and `128_000`/`127_999`) are tested directly, not just comfortably-inside values.
- `createRouterBackedSession` uses a `FALLBACK_ROOT_CONTEXT_WINDOW = 128_000` (lands in "coder-mid") only if `router.resolveModel()` can't resolve the `rlm-root` primary against the `@draht/ai` registry — a defensive default for a case that shouldn't happen with a correctly configured router, not a normal code path.
- **R27-SLM.4 ("per-model config block: `context_window`, `max_sub_calls`, `sub_call_char_budget`, auto-selected template") is satisfied functionally rather than as a literal stored config block.** `context_window` is read live from the resolved model via `@draht/ai`'s registry (`router.resolveModel(...).contextWindow`) rather than duplicated into router config — avoiding a second source of truth that could drift from the model registry. `max_sub_calls`/`sub_call_char_budget` are `createRouterBackedSessionOptions` fields (`maxSubCallBudget` default 50, `subCallCharBudget` default 12_000) supplied per session rather than per-model, since the plan's own factory signature (Architecture section 5) specifies them as session-level options, not fields hung off a router role. Auto-selected template is `selectTier(contextWindow)` as required. No router-config schema change beyond `DEFAULT_CONFIG`'s two new roles and `CostEntry.trajectoryId` was needed to satisfy this requirement.
- Batching advisory (R27-SLM.5) is present in all three templates and is asserted by both a substring test (`prompts.test.ts`, discourages "per item"/"per line"/"per record", recommends 10,000-15,000 char batches) and manual review of each `.md` file — the three templates differ in verbosity/scaffolding (byte-length-distinct, not copy-pasted), per the plan's requirement that they not be cosmetic rewordings of each other.
- `RlmSession` (`session.ts`) itself was untouched, per the plan's explicit instruction — this phase only adds a router-backed factory (`router-session.ts`) that constructs the `rootLlm`/`llmQuery` callbacks `RlmSession` already accepted from Phase 26.
- Cost logging reuses `@draht/router`'s existing `estimateCost`/`logCost` unchanged aside from the additive `trajectoryId` field; `reasoningTokens` is included in the cost entry only when nonzero (`message.usage.reasoning ?? 0`), matching `CostEntry`'s existing optional-field convention.
- Out of scope items (sandboxing, `/rlm` CLI/tool, full trajectory JSONL replay) were correctly left untouched — this phase's cost-log entries are the only durable record produced; Phase 28-30 own the rest.
