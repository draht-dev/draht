# Phase 28, Plan 1: REPL Sandbox & Safety

## Goal
Make the Python REPL execution (Phase 26) actually safe to run LLM-written
code in, and add the resource/budget/state-management guarantees from
R28-SBX.1-6.

## IMPORTANT — this plan was revised after a security-advisor consult (Fable 5), not written from the requirements doc alone
The original draft of this phase (before consult) proposed defending the
sandbox purely in-process: a restricted `__builtins__` dict + a custom
`__import__` hook. **That approach is fundamentally broken and must not be
built as the security boundary.** It passes the acceptance test's literal
three vectors (`import os`, `open(...)`, `urllib.request.urlopen(...)`)
while remaining trivially bypassable via the Python object graph, e.g.:
```python
[c for c in ().__class__.__base__.__subclasses__() if c.__name__ == 'catch_warnings'][0].__init__.__globals__['__builtins__']['__import__']('os').system('id')
(_ for _ in ()).gi_frame.f_builtins['__import__']('os')  # no dunders at all on this route
```
Any function/generator object reachable through the type graph carries its
own `__globals__`/`f_builtins` pointing at the *real*, unrestricted
builtins — swapping the exec globals' `__builtins__` doesn't touch that.
This is why Python's own `rexec`/`Bastion` modules were removed from the
stdlib decades ago and never replaced: in-process confinement of arbitrary
Python is not achievable this way.

**The real security boundary is the OS process boundary, established at
subprocess spawn time.** Python-level restrictions (builtins allowlist,
import allowlist, AST screening) are still worth building, but as
*guardrails for a confused/prompt-injected LLM* (clean errors, keeps it on
the rails, satisfies the acceptance test at the Python level too) — **not**
as the thing that actually stops a deliberately adversarial payload. See
Architecture sections 1 (real boundary) vs. 2 (guardrails) below; don't
blur this distinction when implementing or writing the summary.

## Context
- Threat model: not a human red-teaming the sandbox from outside — an LLM
  whose Python-writing turn might be confused, erratic, or steered by
  adversarial content embedded in `context` (prompt injection instructing
  it to write an escape). The payload author is effectively adversarial
  even though the "attacker" is indirect.
- `sandbox-exec` is confirmed present and working on this dev machine
  (`/usr/bin/sandbox-exec`; a deny-default profile correctly blocked
  `/bin/echo` with "Operation not permitted" during scoping for this plan).
- Wrapping the spawn is additive to `packages/rlm/src/session.ts`'s
  existing `spawn("python3", [DRIVER_PATH])` call — don't rewrite
  `RlmSession`'s core loop, `repl_driver.py`'s wire protocol, or the
  FINAL/FINAL_VAR mechanism. This phase wraps the executor per Phase 26's
  own stated scope boundary ("Phase 28 owns them and will wrap this
  phase's executor, not rewrite it").
- `repl_driver.py` already correctly isolates protocol messages from
  captured user stdout: `_REAL_STDOUT = sys.stdout` is saved once at
  module load *before* any `exec()` can redirect it, and `_write_message`
  always writes through that saved reference while user code's `print()`
  only ever reaches a `io.StringIO()` buffer via
  `contextlib.redirect_stdout`. **Do not regress this** while adding the
  stdout-cap fix below — the fix is capping the *buffer*, not changing
  where protocol messages go.
- Current stdout truncation (per Phase 26's plan) happens **Node-side**,
  after the full `stdout` string already arrives in one `exec_result`
  message — meaning a step doing `print("x" * 10**9)` in a loop can OOM the
  driver *before* Node ever gets to truncate. This phase fixes that by
  capping incrementally on the Python side (see Architecture 5).

## Architecture

### 1. OS-level sandbox (the real security boundary)
New: `packages/rlm/src/sandbox.ts` — platform-dispatching spawn wrapper.

**macOS**: wrap `python3 <driver.py>` with
`sandbox-exec -f <profile.sb> python3 <driver.py>`. Profile
(`packages/rlm/sandbox/macos.sb`, SBPL):
- `(version 1)` `(deny default)`
- `(deny network*)`
- `(deny process-exec*)` — this alone defeats `os.system`/`subprocess`
  (they fork+exec a shell), independent of any Python-level import block.
- `(allow file-read*)` scoped to the Python installation/stdlib paths
  needed to start the interpreter (discover the real paths at profile-
  generation time, don't hardcode a guess).
- `(allow file-read* file-write*)` scoped to exactly the session workdir
  passed in by the caller.
- No `(allow process-fork)` beyond what Python itself needs to start.

**Linux**: wrap with `unshare --user --map-root-user --net --mount -- python3
<driver.py>` (empty net namespace = no interfaces but loopback = network
unreachable at the kernel; mount namespace + bind-mount only the workdir
for FS confinement). If `unshare` isn't available, try `bwrap` with
equivalent flags. Detect availability at startup, don't assume.

**Fail closed**: if neither sandboxing mechanism can be established (spawn
of the wrapper fails, or a startup self-test — below — doesn't confirm
denial), `RlmSession`/the sandbox module must refuse to run at all and
surface a clear `sandbox_violation` init error. Never silently spawn the
driver unwrapped as a fallback.

**Startup self-test**: immediately after the sandboxed driver process
starts (before accepting any root-LLM-authored code), run one internal
`exec` through the normal protocol that attempts a trivial network connect
and a file read outside the workdir, and assert both fail. This is a
runtime proof the sandbox is actually active for *this* process, not just
a one-time manual check during development.

### 2. Python-level guardrails (defense-in-depth, NOT the boundary — say so in code comments)
In `repl_driver.py`:
- **Allowlist, don't blocklist, builtins**: construct the exec globals'
  `__builtins__` from an explicit allowed-names list (safe things like
  `print`, `len`, `range`, `str`, `int`, `float`, `list`, `dict`, `set`,
  `tuple`, `enumerate`, `zip`, `map`, `filter`, `sorted`, `min`, `max`,
  `sum`, `abs`, `round`, `isinstance`, `Exception`-family, etc.) — omit
  `open`, `exec`, `eval`, `compile`, `input`, `breakpoint`, `help`,
  `__import__` (replaced, see below), `getattr`/`setattr`/`vars` (or wrap
  them to a restricted-safe form if genuinely needed — prefer omitting).
- **Import allowlist**: a restricted `__import__` permitting only `re`,
  `json`, `math`, `itertools`, `collections`, `statistics` (per
  R28-SBX.1), raising a clear `ImportError` otherwise.
- **AST pre-screen** (new function, run before every `exec()` call, on the
  raw code string): parse with `ast.parse`, walk the tree, reject with a
  clear driver-level error (not a raw Python exception) if it finds:
  - Any `Attribute` node whose attribute name is a dunder commonly used in
    escapes: `__class__`, `__subclasses__`, `__bases__`, `__base__`,
    `__globals__`, `__builtins__`, `__import__`, `__mro__`.
  - Any `Attribute` node accessing frame-related *non-dunder* names that
    are equally dangerous: `gi_frame`, `f_builtins`, `f_globals`,
    `f_back`, `cr_frame`, `ag_frame` (Fable 5's specific litmus case uses
    `gi_frame.f_builtins` with zero dunders — the dunder-only check
    misses it, so this non-dunder list is required, not optional).
  - Direct `Name`/`Call` references to `eval`, `exec`, `compile`,
    `getattr`, `setattr`, `vars`, `globals`, `locals`, `__import__`.

### 3. Resource limits (corrected — see plan header)
- **Memory**: Node-side RSS polling of the driver child process (every
  ~250ms) via a cross-platform-ish check (Linux: read
  `/proc/<pid>/status` VmRSS; macOS: `ps -o rss= -p <pid>`), hard-`SIGKILL`
  if RSS exceeds the configured ceiling (default 256MB). On Linux only,
  additionally set a generous `RLIMIT_AS` in the driver as a backstop (not
  the primary mechanism, and not used on macOS at all — Darwin's
  enforcement is unreliable and a tight `RLIMIT_AS` can itself break
  interpreter startup on arm64).
- **Time**: Node-side wall-clock per-step timeout (default 30s) is
  primary — if a step's `exec_result` doesn't arrive within the timeout,
  kill the subprocess (this becomes the `timeout` stop reason). Optionally
  also install `signal.setitimer(signal.ITIMER_REAL, timeout)` in the
  driver around each `exec()` to interrupt a runaway pure-Python loop
  in-place (enabling the rollback path below instead of a hard kill) —
  note explicitly in code/docs that this doesn't interrupt a blocked C
  call, so the Node-side kill remains the real backstop.

### 4. Rollback (corrected — diff-based, not deepcopy)
In `repl_driver.py`: before each step's `exec()`, snapshot
`set(globals_dict.keys())`. On a *recoverable* in-process exception (not a
hard kill), remove any keys newly added during the step and restore prior
values only for keys that existed before and got rebound (track via a
shallow per-step "touched names" set populated by comparing pre/post key
sets and, for existing keys, comparing `id()`/equality — don't deep-copy
the whole namespace, and don't attempt to copy the large `context` string
on every step). Document plainly that rollback is impossible after a hard
kill (timeout/OOM/sandbox startup failure) — those map to their own
terminal stop reasons per R28-SBX.6, not a rollback attempt.

### 5. Incremental stdout cap (fixes the OOM-via-print gap)
In `repl_driver.py`: replace the plain `io.StringIO()` capture target with
a small custom file-like wrapper that stops accumulating once it has
buffered `stdout_truncate_chars` (config passed at driver startup, default
2000) worth of output, appending the `[truncated N chars]` marker itself
rather than relying on Node to truncate an already-huge string it had to
receive in full first.

### 6. Budgets & typed stop reasons
In `packages/rlm/src/session.ts` (or a small new wrapper module if that
keeps the diff cleaner — your call, note which in the summary):
- Check `max_iterations`, `max_sub_calls`, and `max_total_cost_usd` (via
  the router-backed session's accumulated cost, Phase 27) **before**
  dispatching each step and **before** each `llm_query` sub-call — not
  just after the fact — so a single step trying to fire many sub-calls (or
  a recursive RLM invocation) is stopped at the boundary.
- Typed stop reasons per R28-SBX.6 (`final | final_var | max_iterations |
  budget_exhausted | timeout | sandbox_violation | error`): wall-clock
  kill → `timeout`; iteration cap → `max_iterations`; sub-call/cost cap →
  `budget_exhausted`; OS sandbox setup/self-test failure or AST-screen
  rejection → `sandbox_violation`; OOM-triggered kill → use `error` with a
  clear message identifying the memory ceiling (there's no dedicated enum
  value for it and R28-SBX.6's list is fixed — don't silently fold it into
  `sandbox_violation`, which should mean "the sandbox itself
  intervened/failed," not "resource exhaustion").

## Risks
- Cross-platform testing: this dev environment is macOS. The Linux
  namespace path (`unshare`/`bwrap`) can't be empirically verified here —
  implement it carefully per documented `unshare`/`bwrap` semantics, mark
  it clearly as "implemented per spec, verify on Linux CI" in the summary,
  and make sure `ci.yml` (which runs on `ubuntu-latest`) actually exercises
  this test suite so it gets real Linux coverage on the next PR/push.
- Don't let the AST pre-screen become so aggressive it breaks ordinary RLM
  usage (task 2's test 4 exists specifically to guard against that).
- Fail-closed behavior must be genuinely closed — test it explicitly
  (task 1's test 7), don't just assume the error path is unreachable in
  practice.

## Out of Scope
- CLI/`/rlm` command, `rlm_query` tool (Phase 29).
- Trajectory JSONL logging/replay/eval harness (Phase 30).
- Container-based sandboxing (Docker/gVisor) — explicitly out of scope
  per the "single persistent subprocess, not a container runtime"
  constraint from the security consult; OS-level wrappers only.
