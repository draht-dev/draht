## Fable 5 Security Review
A Fable 5 security-advisor agent reviewed the implementation after task 3 landed. Verdict: **needs-fix**. Findings and disposition:

1. **OS boundary itself: PASS (verified independently).** The reviewer ran the escape vectors directly under `sandbox-exec`, bypassing `repl_driver.py`'s guardrails entirely, and confirmed the `macos.sb` profile genuinely enforces: `os.system`/`subprocess` blocked (process-exec denied), `open('/etc/passwd')` → `PermissionError`, `socket.create_connection` denied, workdir writes succeed. SBPL last-match-wins ordering, dyld-support import, and framework re-exec handling were all judged sound. No fix needed here.
2. **HEADLINE / needs-fix: `test/sandbox.test.ts` was RED — 6 of 7 tests failed.** Commit `7f2fa2d95` (Python guardrails) landed after the tests were written against a guardrail-free driver and silently broke them: every real-subprocess vector was being intercepted by `repl_driver.py`'s guardrail layer (import allowlist, AST pre-screen) *before* it ever reached the OS sandbox, so the suite proved nothing about the OS boundary and could not distinguish a working sandbox from a disabled one. **Fixed in `9d2397e98`**: tests 2-6 now run plain, guardrail-free Python scripts through `spawnSandboxed` directly (same command/profile wiring, no `repl_driver.py` in the loop), so a disabled sandbox can no longer pass silently.
3. **Required runtime startup self-test was missing entirely**, despite an earlier commit message claiming it existed. **Fixed in `9d2397e98`**: `repl_driver.py` gained a `self_test` wire message that probes a network connect and an out-of-workdir file read using real, unrestricted builtins — deliberately on a route that bypasses its own guardrail layer (routing the probe through the guarded `exec()` path would have given a false positive, the same masking bug as finding 2). `RlmSession` now sends this immediately after spawn/configure and refuses to run (new `sandbox_violation` stop kind) unless both checks report blocked.
4. **Question 3 (Python guardrails framed as defense-in-depth, not the boundary): PASS.** `repl_driver.py`'s docstring/comments and `sandbox.ts`/`macos.sb`'s comments correctly and explicitly state the OS sandbox is the real boundary and the Python-level layer is for a confused/prompt-injected LLM. No fix needed.
5. **Minor (accepted, not fixed): the AST screen is provably non-exhaustive** — `"{0.__class__.__base__}".format(())` reaches the real `object` type at runtime with no `ast.Attribute` node for `__class__` (the screen only sees `.format`). This is expected per the plan (the AST screen was never meant to be complete) and is exactly why the OS-layer test had to be fixed rather than relied upon as redundant — no code change made, noted as an accepted defense-in-depth gap.
6. **Minor: sandboxed child inherited the full parent process environment**, making any parent-process secrets readable via `os.environ` through the same object-graph escapes. **Fixed in `9d2397e98`**: `spawnSandboxed` now passes a small allowlisted `env` instead of the full parent environment.

All three `needs-fix` items (findings 2, 3, 6) were addressed in commit `9d2397e98`; the one PASS-with-caveat item (finding 5) was left as documented, accepted defense-in-depth residue per the plan's own framing.

## Notes
- **Linux namespace path (`unshare`/`bwrap` in `sandbox.ts`) could not be empirically verified on this macOS dev machine.** It is implemented per the plan's documented `unshare --user --map-root-user --net --mount` semantics (empty net namespace = loopback-only = network unreachable at the kernel; mount namespace + workdir bind-mount for FS confinement; `bwrap` as a documented fallback if `unshare` isn't available, detected rather than assumed), but every `sandbox.test.ts` and `resource-limits.test.ts` run in this phase exercised only the macOS `sandbox-exec` branch. This needs real coverage from `ci.yml`'s `ubuntu-latest` runner (confirmed present at `.github/workflows/ci.yml`, running `bun run test` across the monorepo, which includes `packages/rlm`) on the next push — flagging explicitly rather than claiming Linux-path verification that didn't happen.
- Per the plan's explicit scope boundary, `RlmSession`'s core loop, `repl_driver.py`'s wire protocol, and the `FINAL`/`FINAL_VAR` mechanism from Phase 26 were wrapped, not rewritten. The Phase 26 `repl-driver.test.ts` suite (7 tests) needed no changes and still passes unmodified.
- Budget pre-checks (`max_iterations`, `max_sub_calls`, `max_total_cost_usd`) run *before* dispatch at each step and before each `llm_query` sub-call, per R28-SBX — `resource-limits.test.ts` tests 5 and 6 assert the stop happens at the correct call, not after overshooting.
- Typed stop reasons implemented per R28-SBX.6: `final | final_var | max_iterations | budget_exhausted | timeout | sandbox_violation | error`. OOM-triggered kills surface as `error` with a message identifying the memory ceiling (there's no dedicated enum value for it, and `sandbox_violation` is reserved for "the sandbox itself intervened/failed," not general resource exhaustion), matching the plan's explicit instruction not to fold OOM into `sandbox_violation`.
- Container-based sandboxing (Docker/gVisor), the `/rlm` CLI command, `rlm_query` tool, and trajectory JSONL logging/replay were correctly left out of scope, owned by Phases 29-30.
