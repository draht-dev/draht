# Phase 29, Plan 1: Draht Agent & CLI Integration

## Goal
Make `@draht/rlm` (Phases 26-28) actually reachable from the coding-agent CLI
and from other agent flows, per R29-INT.1-5.

## IMPORTANT — this is exactly the class of bug found and fixed earlier this session, don't repeat it
Phase 23 built `core/builtins/subagent.ts` (including the permission gate)
fully tested in isolation, but it was **never actually loaded by any real
session** — nothing in `main.ts`/`agent-session.ts`/`sdk.ts` referenced it,
because the real extension-loading path is settings-driven
(`DefaultPackageManager.resolve()` reading `settingsManager`'s `packages`
array), not automatic directory scanning. That gap went undetected until an
explicit post-hoc audit traced every call site.

Separately, while scoping *this* phase, a strong signal emerged that the
**same bug likely already exists** in `packages/knowledge` (Phase 5),
`packages/ci` (Phase 6), and `packages/deploy-guardian` (Phase 9): none of
their `package.json` files have the `"pi": { "extensions": [...] }` manifest
field that `packages/coding-agent/src/core/package-manager.ts`'s
`resolveExtensionEntries()` looks for, and none has a root `index.ts`/
`index.js` (the fallback `resolveExtensionEntries` checks) — only a
`src/index.ts`, which isn't discovered by that function at the package root.
**Investigating and fixing those three packages is explicitly out of scope
for this plan** (it's a pre-existing, unrelated finding, not something to
fix as a side effect of RLM work) — just don't copy their pattern
uncritically as "the reference implementation," and flag the finding in the
summary for a future phase/task to reconcile.

**For `packages/rlm-agent` specifically**: give its `package.json` a correct
`"pi": { "extensions": ["./src/extension.ts"] }` manifest field, and — this
is the must-have, not optional — write an integration test that goes through
the REAL settings-driven resolution path (construct a session via
`createAgentSessionServices`/`createAgentSessionFromServices` from
`@draht/coding-agent`'s `src/core/agent-session-services.ts`, with a
`settingsManager` configured to include a **local package source** pointing
at the `packages/rlm-agent` directory — read
`packages/coding-agent/src/core/package-manager.ts`'s `parseSource`/local-
source handling to get the exact source-string format right), then assert
the `/rlm` slash command and `rlm_query` tool actually appear in a real
session's registered commands/tools. Do not settle for only testing the
extension factory function in isolation (that alone is exactly what gave
Phase 23 false confidence).

## Context
- CLI subcommand dispatch point: `packages/coding-agent/src/main.ts` around
  lines 491/504 — `handlePackageCommand(args, ...)` and
  `handleConfigCommand(args, ...)` (from `./package-manager-cli.ts`) are
  checked early; if either returns `true`, `main()` short-circuits before
  starting the interactive session. A new `draht rlm --input ... --query
  ...` subcommand follows the same pattern: a `handleRlmCommand(args, ...)`
  check alongside them. Read `package-manager-cli.ts` first to match its
  argument-parsing/output conventions.
- `/execute-phase` (R29-INT.5) is **not TypeScript code** — it's a prompt
  template at `packages/coding-agent/prompts/commands/execute-phase.md`
  (and its compiled mirror in `dist/`) that instructs the LLM on what to do.
  Adding `rlm: true` GSD-plan-frontmatter routing means **editing this
  prompt template** to add instructions like "if the plan's frontmatter has
  `rlm: true` and an input file exceeds a size threshold, use the
  `rlm_query` tool instead of reading it directly" — this is a
  documentation/prompt-engineering change, not new application code. Don't
  over-engineer a code-level enforcement mechanism for this requirement.
- `@draht/knowledge`'s public API (`packages/knowledge/src/client-config.ts`,
  `knowledge-manager.ts`): `loadClientConfig(cwd): ClientConfig | null`,
  `getKnowledgePath(slug)`, `getKnowledgeDbPath(slug)`, `KnowledgeManager`
  class. R29-INT.4's loader should call into these directly, not
  reimplement client-config discovery.
- `@draht/rlm`'s existing exports (Phases 26-28):
  `RlmSession`/`createRouterBackedSession` (Phase 26/27),
  `spawnSandboxed`/sandbox wiring (Phase 28, already the only spawn path —
  don't bypass it). This phase adds *input loaders* (file/glob/URL/knowledge)
  and *integration surfaces* (extension, CLI, tool) on top; it doesn't touch
  the session/sandbox internals.
- The 500KB+ fixture acceptance test needs a real (or realistic synthetic)
  large text file — generate one as a test fixture, don't assume one exists.

## Architecture

### 1. Input loaders (`packages/rlm/src/loaders.ts`)
```ts
export type InputSource = { type: "file"; path: string } | { type: "glob"; pattern: string; cwd: string } | { type: "url"; url: string } | { type: "knowledge"; clientSlug: string };
export function parseInputArg(input: string, cwd: string): InputSource; // "path/glob" vs "http(s)://..." vs a recognized client-knowledge reference — document the exact syntax you choose for the knowledge case
export async function loadInput(source: InputSource): Promise<{ content: string; contextType: string }>;
```
File/glob loaders read and concatenate (with clear separators noting each
source file's path) via Node fs/glob; URL loader does a plain `fetch` (no
special sandboxing needed here — this runs in the main Node process
building the prompt, not inside the RLM sandbox); knowledge loader calls
`@draht/knowledge`'s `loadClientConfig`/`KnowledgeManager` to pull a
client's AGENTS.md + past decisions into one combined context string.

### 2. `packages/rlm-agent/` extension package
New workspace package, `@draht/rlm-agent`. `package.json` with the `pi`
manifest field per the IMPORTANT section above. `src/extension.ts` default-
exports an `(pi: ExtensionAPI) => void` (read
`packages/coding-agent/src/core/builtins/subagent.ts`'s default export for
the shape/conventions, since it's the most recent working example of an
extension factory in this codebase) registering:
- A `/rlm <input> <query>` slash command (or `pi.registerTool`/whatever
  mechanism draht extensions use for slash commands — check an existing
  extension like `packages/compliance/src/extension.ts` for the actual
  registration API) that parses `input` via `parseInputArg`, loads it,
  constructs a `createRouterBackedSession`, runs it, and returns the answer.
- An `rlm_query` tool (`pi.registerTool`) usable from normal agent flow —
  `{ input: string, query: string }` params, same load-and-run path,
  returning the RLM session's final answer as the tool result. This is
  what lets a normal agent defer an oversize read instead of dumping it
  into its own context.

### 3. CLI subcommand (`packages/coding-agent/src/rlm-cli.ts` or add to `package-manager-cli.ts` if that's a better fit — your call, say which in the summary)
`draht rlm --input <path|glob|url> --query "..." [--max-cost 1.00]`:
parses args, calls the same `loaders.ts` + `createRouterBackedSession` path
as the extension, prints the answer, exits. Wire the dispatch check into
`main.ts` alongside `handlePackageCommand`/`handleConfigCommand` per the
Context section.

### 4. Knowledge-base loader integration (R29-INT.4)
Already covered by the `"knowledge"` `InputSource` variant in section 1 —
this section is just the acceptance criterion, not separate new code.

### 5. GSD `/execute-phase` prompt update (R29-INT.5)
Edit `packages/coding-agent/prompts/commands/execute-phase.md` (and check
whether `dist/prompts/commands/execute-phase.md` is a build artifact that
regenerates from the source, or needs the same edit applied twice — check
the package's build script) to add: plans may declare `rlm: true` in their
frontmatter; when true, and an input file referenced by a task exceeds a
stated size threshold (pick one, e.g. 200KB, and say why), the executing
agent should use the `rlm_query` tool (section 2) instead of reading the
file directly into its own context.
