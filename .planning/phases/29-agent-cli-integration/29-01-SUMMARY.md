## Notes on the real-session-loading test (must-have, verified genuine)
Read `packages/rlm-agent/test/real-session-loading.test.ts` directly to confirm it does what the plan demanded, not just what its name claims:
- It calls the actual `SettingsManager.create(tempDir, agentDir)` → `createAgentSessionServices({ cwd, agentDir, settingsManager })` → `createAgentSessionFromServices({ services, sessionManager, model })` chain — the same construction path `@draht/coding-agent`'s own CLI uses — rather than any test-only bypass such as passing `resourceLoaderOptions.extensionFactories` directly.
- The local package source is a `settings.json` file written to disk (`{ packages: [RLM_AGENT_PACKAGE_DIR] }`) containing an **absolute path to the real, on-disk `packages/rlm-agent` directory** (derived from `import.meta.url`, one level up from the test file itself) — not a copied fixture — matching exactly what `DefaultPackageManager.parseSource()` (any non-`npm:`/non-git-URL string → `{ type: "local", path: source }`) and `resolveLocalExtensionSource()` → `collectPackageResources()` (reads the package's `"pi": { "extensions": [...] }` manifest field) resolve at runtime. I independently confirmed this reading against `packages/coding-agent/src/core/package-manager.ts` itself (`parseSource` at the cited line, `resolveLocalExtensionSource`/`collectPackageResources` immediately following) — the test's own header comments accurately describe the real code, they aren't just asserted in a comment and then contradicted by the implementation.
- It asserts on the real session object: `session.getAllTools().map(t => t.name)` contains `rlm_query`, and `session.extensionRunner.getCommand("rlm")`/`getRegisteredCommands()` show the `/rlm` command registered.
- Critically, it includes a **negative control**: a third test builds an identical real session with no `settings.json` (empty `packages` array) and asserts `rlm_query`/`/rlm` are *absent*. Without this, the first two assertions would be equally consistent with "these tools/commands are always present in every session regardless of package config" — a false-positive shape the Phase 23 postmortem specifically flagged as the thing to guard against. With it, the test suite actually distinguishes "loaded because configured" from "loaded unconditionally."
- It deliberately stops short of invoking `rlm_query.execute()` or the `/rlm` handler (both would spawn a real OS-sandboxed `python3` subprocess and need a live model provider key) — that's out of scope for "is it reachable," and is covered by `@draht/rlm`'s own Phase 26-28 test suites instead.

This is the same class of proof the Phase 23 `core/builtins/subagent.ts` fix used (see `.planning/STATE.md`'s 2026-07-11 audit-log entry): construct a real session through the real settings-driven path and assert on its actual registered surface, not on the extension factory function called in isolation against a mock.

## Flagged, Out-of-Scope Finding (restated for visibility)
While scoping this phase, a strong signal emerged that **the same extension-loading gap Phase 23 had** (a real session never actually loading an extension package because nothing referenced it through the settings-driven resolution path) **likely already exists in three other packages**:
- `packages/knowledge` (Phase 5)
- `packages/ci` (Phase 6)
- `packages/deploy-guardian` (Phase 9)

None of their `package.json` files has the `"pi": { "extensions": [...] }` manifest field that `packages/coding-agent/src/core/package-manager.ts`'s `resolveExtensionEntries()` looks for, and none has a root `index.ts`/`index.js` (the fallback `resolveExtensionEntries` checks) — only a `src/index.ts`, which the package-root fallback does not discover. This was **not investigated or fixed** as part of this plan — it's a pre-existing, unrelated finding surfaced incidentally while getting `packages/rlm-agent`'s own manifest right, explicitly called out in the plan's "IMPORTANT" section and "Risks" as scope creep to resist. `packages/rlm-agent/package.json` itself was given the correct manifest field (see Files Changed above) precisely so it does not repeat this pattern.

**Recommended as a follow-up task for a future phase**: audit `packages/knowledge`, `packages/ci`, and `packages/deploy-guardian` the same way Phase 23 was audited — trace every real call site (`main.ts`, `agent-session.ts`, `agent-session-services.ts`, `sdk.ts`) to determine whether any of the three is ever actually loaded by a real session today, or whether all three have been silently-dead-on-disk since their respective phases landed — then add the missing manifest field (or root entry point) and a real-session-loading regression test per package, following this phase's `real-session-loading.test.ts` as the template.

## Notes
- **Loaders (`packages/rlm/src/loaders.ts`) are exported from `@draht/rlm`'s package root**, not left as an internal `src/` implementation detail, specifically so `@draht/rlm-agent` and `packages/coding-agent/src/rlm-cli.ts` both consume the same public entry point rather than reaching across package boundaries into another package's `src/`.
- **`--max-cost` is parsed and validated by the CLI but not yet enforced against the run.** `createRouterBackedSession`/`RlmSessionOptions` (Phases 26-28) have `maxTotalCostUsd`/cost-accounting fields, but the router-backed session factory doesn't currently pass a cost ceiling through from the CLI. This is called out directly in `rlm-cli.ts`'s own module docstring as a known gap, deliberately left unwired rather than widening this plan's scope back into `router-session.ts` internals — flagged here as a follow-up rather than silently shipped as "done."
- **`dist/prompts/commands/execute-phase.md` is a build artifact, not a second source of truth.** `packages/coding-agent/package.json`'s `copy-assets` script (`shx rm -rf dist/prompts ... && shx cp -r prompts dist/prompts`) regenerates `dist/prompts/` from the top-level `prompts/` directory at build time; the source-of-truth edit was made once, at `packages/coding-agent/prompts/commands/execute-phase.md`, and a diff against the currently-checked-in `dist/` copy (stale until the next build) confirms it contains exactly the new section, nothing more or less — no double-edit was needed or performed.
- `/rlm`'s command handler and `rlm_query`'s tool `execute()` both share one `runRlmQuery()` helper (extension side) with `handleRlmCommand`'s equivalent logic (CLI side) rather than each reimplementing the load → prompt-build → session-run → format sequence independently — kept as two call sites over the same `@draht/rlm` loader/session primitives, not a shared cross-package helper, since the extension and CLI have slightly different surrounding conventions (`ctx.ui.notify` vs `console.log`/`process.exitCode`).
- Per the plan's explicit scope boundary: `RlmSession`'s core loop, the Python REPL driver, and the OS sandbox (Phases 26-28) were used as-is and not modified by this phase's work. Trajectory JSONL logging/replay/eval harness and publishing `@draht/rlm-agent` externally were correctly left out of scope, owned by Phase 30 (and beyond, respectively).
- The packages/knowledge/ci/deploy-guardian extension-loading finding above is restated in `.planning/STATE.md`'s Audit Log as a recommended follow-up for a future phase.
