# /brainstorm

Topic: $ARGUMENTS

Read relevant project context, then help the user choose an approach. Ask only questions that materially affect the result; group related questions and provide recommendations when useful. Distinguish accepted decisions from assumptions.

Compare alternatives where there is a real trade-off. Describe the intended outcome, scope, constraints, approach, risks, and observable success criteria at the depth the task needs. Do not impose a fixed number of rounds or section-by-section approvals.

A concise recommendation in chat is sufficient. Write a design document when requested or useful for substantial work, in the project's established location. Do not require `.planning/`, a new session, or a GSD command. Use those only when the user selected GSD.

When the user asks to implement, proceed within that authorization. Clarify only blocking decisions or actions that need additional permission. Brainstorming is not a gate on otherwise clear implementation requests.
